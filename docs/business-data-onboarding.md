# 问渠 WenQu 业务领域与数据接入手册

> 基准日期：2026-09-08
> 适用对象：业务负责人、数据工程师、平台管理员、安全人员和 Agent 开发者。
> 目标：在公司内部单一环境中，用最小范围把一个真实业务领域从“业务定义”接到“可查询、可同步、可验收”，再验证第三方 Agent 能否复用同一能力。

> 第一性目标：**让业务语义成为企业资产，让数据库成为数据来源，让 Agent 成为能力消费者。** 接入时先确认业务对象、关系和口径，再配置表、字段和 SQL 映射；不能从物理表结构反向替代业务定义。

## 1. 先说清当前边界

- 当前数据源接入只支持 **MySQL**，业务库使用只读账号。
- 平台采集表结构和执行查询时不修改业务库；Ontology 同步也是只读。
- 当前同步由页面/API 触发，不是 CDC 或后台定时同步。
- Ontology Action 当前只更新管理库中的对象和 overlay，不直接写回 ERP、贷款核心或其他生产系统。
- `admin/user` 只是当前系统管理和演示验证的登录门禁；平台实际使用对象以业务人员、技术人员为主，正式角色边界等真实业务接入后再确认，不扩建独立“普通用户”产品体系。
- 数据源页已提供按业务领域维护的表/列权限和脱敏配置；表白名单默认拒绝，未明确允许的表不能进入查询、对象和同步链路。Agent 权限只保留为旧领域迁移兼容。
- 本项目内置 Agent 只是调试/回归客户端；当前对话可显式选择业务领域，未选择时才回退 Agent 默认领域。首个真实试点建议“一个业务领域 + 一个业务数据源 + 一个验证 Agent”，但能力验收必须同时准备外部 Agent 调用样例。

真实业务接入前，至少先完成“只读账号、表白名单、敏感字段、对象主键、指标口径、验收问题”六项确认。

## 2. 最小试点范围

首个领域不要一开始接全库，建议硬性控制为：

- 1 个公司内部环境、1 个业务领域、1 个只读数据源。
- 3–8 张核心表，优先事实表和必要维表。
- 3–5 个业务对象、2–3 条关系、3–5 个 Query 指标/维度。
- 1 个内置验证 Agent，5–10 条业务验收问题，并保留一条外部 Agent 调用记录。
- 至少 1 次小批量对象同步和 1 条越权/敏感字段阻断验证。

## 3. 角色分工

| 角色 | 主要责任 | 需要确认的结果 |
|---|---|---|
| 业务负责人 | 说明业务范围、对象、指标、状态和规则 | “业务上这样理解” |
| 数据工程师 | 准备只读连接、表清单、字段含义和更新时间 | “数据里确实有这些字段” |
| 平台管理员 | 创建领域、采集 Schema、录入模型、校验发布和配置 Agent | “系统可以稳定运行” |
| 安全人员 | 确认允许表、敏感列、脱敏和账号边界 | “谁可以看什么” |
| Agent/应用开发者 | 用已发布能力配置场景交互和调用 | “内置验证客户端与外部应用能按同一契约消费” |
| 业务用户 | 使用标准问题并反馈差异 | “结果能不能用于业务” |

## 4. 十步接入流程

| 步骤 | 负责人 | 输入 | 产物 / 完成条件 |
|---|---|---|---|
| 1. 定范围 | 业务负责人 | 目标流程、非目标流程、3–5 个核心问题 | 领域卡；范围和验收人明确 |
| 2. 建领域 | 平台管理员 | 领域名称、`domain_key`、负责人 | 在公司内部模型库中，由管理员在 `/enterprise-model` 的“语义与数据”子区创建/选择业务领域 |
| 3. 准备数据源 | 数据工程师 + 安全人员 | MySQL 地址、库名、只读账号、网络要求 | 连接测试成功；密码不写文档或 bundle |
| 4. 选核心表 | 业务负责人 + 数据工程师 | 表清单、粒度、主键、更新时间字段 | 3–8 张表白名单；不直接采全库 |
| 5. 采集 Schema | 平台管理员 | 已确认的表名 | `meta_table/meta_column`；核对字段类型、PK/FK 和注释 |
| 6. 配置权限 | 安全人员 + 平台管理员 | 业务领域、表/列清单、脱敏要求 | 配置领域级允许/拒绝/脱敏规则；完成一条允许和一条阻断测试 |
| 7. 建企业模型 | 业务负责人 + 平台管理员 | 对象、关系、指标、规则、映射 | 每个对象有稳定主键和来源；每个指标有口径和标准问法；核对 Ontology/语义桥接警告 |
| 8. 校验并发布 | 平台管理员 + 业务负责人 | 语义快照、Ontology 发布、映射和权限 | 创建 `enterprise_model_release`，服务端校验通过后激活；记录三层版本和确认人 |
| 9. 小批同步 | 平台管理员 + 数据工程师 | 激活模型和 `source_query` | 先预览再执行；每类对象同步一页，对象数、主键、样例、来源和运行 trace 可核对 |
| 10. 能力与 Agent 验收 | Agent/应用开发者 + 业务用户 | Query 能力、验证 Agent、外部调用样例、标准问题集 | 内置与外部调用使用同一模型版本、能力和 LogicForm；各自 trace 可关联，差异有记录 |

当前 UI 的对应入口：数据源在 `/datasource`，语义和本体在 `/enterprise-model`，同步在 `/twin-runtime`，能力核对在 `/capability-center`，内置验证 Agent 配置在 `/agent`。业务人员当前主要参与确认和验收，不能在页面维护公司级治理配置、权限或发布模型。

## 5. 业务建模时只需要确认这些内容

业务人员不必先写 SQL 或技术 key，只需确认业务定义；技术 key、映射 SQL 和权限由平台/数据人员落配置。当前页面只允许管理员编辑“语义与数据”并发布，业务负责人先以评审和验收角色参与。

### 5.1 对象卡

| 字段 | 示例 | 说明 |
|---|---|---|
| 业务名称 | 贷款申请单 | 一笔可独立识别的业务记录 |
| 定义 | 客户提交的一次贷款申请 | 不要把“审批流程”当成对象 |
| 主键 | application_id | 必须稳定、唯一、可回查 |
| 展示字段 | application_no | 业务人员看到的名称/编号 |
| 来源 | `loan_application_indicator` | 表或受控 `source_query` |
| 当前状态 | approval_status | 只写清状态值含义 |
| 负责人 | 业务域负责人 | 后续口径争议找谁确认 |

建模边界：对象表示“谁/哪一笔记录”，事件表示“发生过什么”，状态表示“现在处于哪一步”，动作表示“允许做什么”。

### 5.2 关系卡

确认“谁和谁通过什么字段关联”：

```text
客户(customer_id) 1 ── N 贷款申请(customer_id)
贷款申请(application_id) 1 ── 0..1 贷款账户(application_id)
```

没有可靠连接键时先标记为“待验证”，不要让模型自行猜 JOIN。

### 5.3 指标卡

每个指标至少确认：名称、业务定义、统计粒度、分子/分母、时间字段、可分组维度、默认过滤、来源表/字段、示例问法和预期结果容差。

例如：

```text
指标：贷款申请数量
粒度：一行 = 一笔申请
默认聚合：COUNT(application_id)
可分组维度：approval_status、channel、region
示例问法：按申请渠道统计当前申请数量
```

“数量”“总数”“当前”“申请渠道”等业务词必须和标准 key/字段一一核对，避免同名字段跨表误映射。

## 6. 数据与权限验收

### 6.1 数据质量最小检查

- 表是否确实代表目标业务粒度；一行到底是一笔申请、一个账户还是一条流水。
- 主键是否存在、唯一、稳定；没有主键要记录风险，不直接进入对象同步。
- 时间字段、时区、更新时间含义是否明确。
- 枚举值（状态、渠道、类型）是否有业务字典。
- 关键字段抽样是否和业务页面/人工报表一致。
- 跨表 JOIN 是否有明确键和基数；没有外键时由业务和数据人员共同确认。

### 6.2 权限验收

```text
用户 / 外部调用方
  → 可访问业务领域与已发布能力
  → 业务领域绑定数据源
  → 表级允许/拒绝
  → 列级允许/脱敏
  → SQL 安全校验
  → 结果脱敏
```

旧领域尚未配置领域级规则时，可以显式回退已绑定验证 Agent 的旧权限；该路径只用于迁移，运行 trace 会记录兼容来源。

至少保留两条测试：

1. 允许查询：能读取已授权表和非敏感字段。
2. 阻断查询：访问未授权表或敏感列时被拒绝/脱敏，并记录原因。

接入真实库前还要重点验证：领域不绑定验证 Agent 时，领域级权限仍能独立完成查询与同步；对象查询不会把已落库的敏感属性直接返回；内置验证 Agent 和外部 Agent 只消费同一激活模型版本。

## 7. 发布、同步和回滚边界

建议按下面的顺序验收：

```text
草稿
  → 映射/权限/质量检查
  → 校验
  → 发布 release
  → 小批同步
  → 标准问题验收
  → 扩大同步范围
```

- `examples/loan/semantic-domain.json` 是查询语义 bundle；`examples/loan/ontology-bundle.json` 是 Ontology bundle，两者不能混用。
- 示例 bundle 的固定 ID 只适用于演示；真实接入必须先创建领域和数据源，再使用真实 ID 导入并核对绑定。导入后分别生成语义快照和 Ontology 发布，再在“版本发布”中组成统一企业模型版本并激活。
- `seed_*.py` 是合成数据初始化脚本，不得对真实业务库运行。
- 当前支持统一模型停用和回滚，但不会自动回滚已经同步的对象数据；CDC、删除检测和身份冲突处理仍未实现。发现问题时先停同步、保留运行记录，再回滚模型或人工修正数据。

## 8. 标准验收问题模板

每条问题都要记录：

| 项目 | 内容 |
|---|---|
| 问题 | 业务人员实际说法 |
| 预期对象/指标 | canonical key 和业务名称 |
| 预期维度/过滤 | 例如 `channel`、`approval_status`、时间范围 |
| 应命中表/字段 | 允许的物理表和字段 |
| 预期结果 | 数值、分组、容差或人工判断 |
| 实际结果 | 答案、SQL、错误或未命中原因 |
| 追踪信息 | `trace_id`、`domain_id`、`ontology_release_id` |
| 结论 | 通过 / 修改映射 / 修改业务口径 / 暂不支持 |
| 确认人和日期 | 业务负责人、平台管理员、绝对日期 |

首轮至少覆盖：总量、分组、时间、跨表、状态/渠道、敏感字段拒绝和一个无权限场景。

## 9. 当前接入前的验收门槛

代码层已经完成默认拒绝权限、对象/关系/Action 脱敏、同步权限主体、统一激活版本和外部 Query 调用审计。真实数据进入前仍必须留下以下验收记录：

1. 在真实测试库完成允许表、拒绝表、禁止字段、别名脱敏和无权限调用测试。
2. 业务负责人确认对象主键、关系键、指标口径和 5–10 条标准问题的预期结果。
3. 每类对象先 dry-run，再小批执行；核对真实落库值、脱敏响应、数量和错误摘要。
4. 内置验证 Agent 与外部 Agent 使用同一 `domain_id + model_release_id + capability_key + LogicForm` 得到可比结果，并保留各自 trace。
5. 当前一个领域只绑定一个默认 `datasource_id`；涉及多库或跨源 JOIN 时必须另行设计，不可直接接入。

完成上述真实测试库验收前，只接入脱敏测试库或合成数据，不接生产敏感表。

## 10. 示例资产怎么用

| 示例 | 用途 | 不能当作什么 |
|---|---|---|
| `examples/loan` | Ontology、查询语义和风险交付完整技术演示 | 真实授信规则或生产接入模板 |
| `examples/douyin_ecommerce` | 数据源、Schema 和语义资产自动初始化演示 | 真实库初始化脚本；会重建合成表 |
| `examples/supply_chain` | Ontology bundle 导入演示 | 完整数据源/表接入方案 |
