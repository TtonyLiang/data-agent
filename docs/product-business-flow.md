## 2. 当前业务方向

问渠 WenQu 当前定位为：

> **公司内部使用的 Ontology 驱动企业运营数字孪生与智能决策平台。平台把公司的业务理解和数据组织为 AI 可消费的统一业务模型与标准能力，作为企业智能中枢和决策引擎。**

本项目的第一性目标是：**让业务语义成为企业资产，让数据库成为数据来源，让 Agent 成为能力消费者。**

因此，业务对象、关系、状态、规则、动作、指标和发布版本属于企业模型；数据库表、字段、SQL、API 和文件是数据来源或实现映射；Agent/业务应用只能按授权消费已发布模型和能力。任何新功能都必须说明自己是在沉淀企业语义、连接数据来源，还是提供能力消费，不能把某个 Agent 或某条 SQL 当成业务资产本身。

平台目标不是把所有业务都放进一个聊天窗口，也不是把 Agent 做成平台边界，而是先建设可被不同 Agent 和业务应用复用的企业级底座：

```text
数据库 / API / 文件 / 业务事件
-> 业务领域
-> 企业模型中心
-> 数据处理与孪生运行时
-> Query / Decision / Action Capability
-> 第三方 Agent / 业务应用
-> 结果反馈与决策审计
```

财税报告交付、贷款风控、智能问数是平台上的垂直应用与验证场景。当前以贷款合成数据验证技术闭环；其规则、阈值和结论不是已经验证的财税、审计、合规或授信规则。

当前阶段的第一目标是把三块基础能力做扎实：

1. **企业模型中心**：统一业务对象、关系、指标、规则、映射、状态、动作、权限和版本。
2. **数据处理与孪生运行时**：把源数据转换为有身份、有状态、有来源的业务对象。
3. **能力发布中心**：把模型和数据转成 Agent 可稳定调用的查询、决策和动作能力。

Agent 是这些企业资产和能力的消费者。本项目内置的 Agent/对话仅用于调试、回归和验收，第三方 Agent 不需要先在本项目创建 Agent；对话功能当前只需验证能力消费效果，不是近期建设重心。

## 3. 功能块如何联动

| 功能块 | 主要职责 | 与其他模块的关系 |
|---|---|---|
| 公司级治理与业务领域 | 管理公司内部用户、业务范围、模型和数据访问边界 | 业务领域持有模型、数据映射、版本和能力；Agent/应用按授权消费领域 |
| 企业模型中心 | 统一管理原“查询语义”和“本体建模”资产 | 对象语义回答“业务里有什么”，指标与映射回答“数据在哪里、怎么算”，状态与动作回答“现在怎样、可以做什么” |
| 数据源与孪生运行时 | 连接业务数据，映射、同步并查询对象实例 | 已支持受权限控制的预览/手动执行、运行记录和激活版本校验；生产级增量同步和身份解析后续建设 |
| 能力发布中心 | 发现和调用 Query / Decision / Action Capability | 已提供第三方调用身份、Query 授权、标准调用和摘要审计；Decision/Action 外部出口后续建设 |
| 验证 Agent 与对话 | 作为平台内置参考客户端消费已发布能力 | 只用于调试、回归和验收，不拥有领域与本体资产，也不是第三方 Agent 注册中心 |
| 风险交付 | 管理风险事项、证据、人工复核、报告版本和审计 | 是财税/贷款垂直验证场景，用于证明模型、数据、能力和决策审计可以形成闭环 |
| 模型配置 / Prompt / 系统参数 | 管理模型、提示词、召回阈值和运行参数 | 支撑理解与生成，但不替代企业模型、规则和权限 |
| 当前系统访问控制 | 业务人员/技术人员职责边界；兼容旧 `admin/user` 账号和验证 Agent | `admin/user` 只承载兼容权限，不作为额外产品角色 |

### 3.1 为什么需要“业务领域”

本项目只有一个公司内部环境，不建设多企业空间或租户层级。业务领域的作用是把复杂业务拆成可独立梳理、发布、验收和复用的范围。

- **业务领域**回答：这是客户、财税、授信还是风险管理模型，由谁负责，使用哪些数据和规则。
- **企业模型**回答：业务对象、指标、关系、状态、规则和动作是什么。
- **Agent/应用**回答：哪个场景需要调用哪些已经发布的能力。

目标业务关系为：

```text
公司内部统一模型库
  -> 业务领域
      -> 企业模型 / 数据映射 / 发布版本 / 能力
          -> 本项目验证 Agent 与第三方 Agent 按授权消费
```

因此，同一“客户”模型不需要为不同 Agent 重复建三遍。领域下线或更换验证 Agent 时，企业模型仍作为公司资产保留。

企业模型页面按以下顺序操作，业务领域由公共顶部统一创建和选择，三个步骤共享同一套对象、语义资产和发布上下文：

```text
创建 / 选择业务领域
  → 业务模型
      → 业务对象与动作
      → 按对象维护指标与业务规则
  → 数据绑定
      → 对象数据源 / 指标计算 / 关系连接 / 字段映射
  → 校验发布
      → 草稿校验 / 快照 / 统一版本 / 激活 / 检索索引
```

当前开发验证阶段由项目开发者使用 `admin` 账号贯穿完成业务建模和技术配置；业务人员与技术人员的第一版编辑边界已经落实到页面和 API，真实人员接入后再进行账号分配和实际业务验收。页面继续把业务定义和技术数据绑定按任务分区，不新增第三类工作模式或产品角色。

当前运行链路仍保留 Agent-领域绑定和默认领域字段，这是历史问数适配层，不是企业模型的所有权关系。后续对外能力接口应以 `domain_id + release_id + caller context` 为主。

### 3.2 企业模型中心：统一查询语义与 Ontology

两者不是两套互相独立的产品，而是同一个企业业务模型的两类资产：

- **查询语义负责聚合分析**：指标是什么、维度是什么、映射到哪张表哪个字段、如何 JOIN、如何生成 SQL。
- **Ontology 负责业务对象与动作**：客户、申请、账户、风险快照等对象当前是什么状态，可以执行什么动作，动作会怎样改变状态。

当前实现里，事件和状态还没有独立的事件流运行时：状态主要保存在对象属性、动作效果和本地覆盖值中，状态变化通过动作记录与审计记录留痕；独立事件对象、历史状态时间线和持续事件订阅属于后续孪生运行时建设。

产品上统一为“企业模型中心”，共同使用业务领域、稳定 `object_key` 和发布版本。页面以本体对象为中心组织查询词汇、指标和业务规则；底层 `semantic_*` 与 `ontology_*` 表继续兼容。查询语义指导 LogicForm 和 SQL，Ontology 对象、关系和动作证据参与业务理解及 Schema 打分。

#### 对象、事件、状态和动作的边界

Ontology 中的“对象”不只指客户、账户这类物理实体，也可以是有业务身份和生命周期的申请单、订单、交易或案件。建模时应区分四层：

| 层次 | 用途 | 贷款示例 |
|---|---|---|
| 对象 | 可独立识别、可查询、可关联的业务实体或业务记录 | 贷款申请单、贷款账户、催收案件 |
| 事件 | 记录某个时间点发生的业务事实 | 提交申请、审批通过、放款 |
| 状态 | 表示对象当前处于哪个阶段 | 待审核、已通过、逾期 |
| 动作 | 对对象执行的受控业务操作 | 审批申请、发起催收、结案 |

“贷款审批流程”是流程规则，不应直接命名为 `LoanApplication`；`LoanApplication` 应明确表示“一笔申请单”。如果需要记录每次审核的人员、时长、意见和状态变化，可以增加 `ApprovalReview` 或状态变化事件/历史对象。

### 3.3 数据处理与孪生运行时

运行时负责把“数据库里的行”转换为“业务里的对象”：

```text
源数据 -> 字段映射 -> 对象身份 -> 当前状态 -> 关系 -> 来源与更新时间
```

当前已经有业务库只读对象同步、对象实例查询，以及 `source_properties + overlay_properties` 的状态合并。P0 新增统一的“孪生运行”可见入口，但仍由页面或 API 触发同步，不是后台定时任务或 CDC。

后续重点是定时/增量同步、跨系统同一对象识别、状态变化历史、数据质量、冲突处理、血缘和运行监控。

### 3.4 能力发布中心与 Agent

能力中心把内部实现转换为外部 Agent 可依赖的稳定契约：

- `Query Capability`：只读对象查询、过滤、关联、聚合和指标计算。
- `Decision Capability`：基于规则或模型形成判断、原因和建议，后续建设。
- `Action Capability`：创建、修改、审批、状态变化或外部写回等受控操作。

当前已有对象查询、第一版 Query Capability 和仅供内部验证的 Action 工具。能力中心当前对外发布 Query，内部 Action 只用于本项目验证；正式发布版本、输入输出 Schema 治理、灰度、限流、配额、依赖分析和生产级调用网关仍属于后续。

### 3.5 风险交付是垂直验证场景

风险交付把对话和 Ontology 连接成完整业务流程：

- 从对话结果创建风险事项时，系统按 `agent_id + session_id + trace_id` 精确找到问数轮次。
- 自动冻结问题、LogicForm、SQL、结果预览、分析产物等查询证据。
- 用户可选一个 Ontology 对象，额外冻结该对象的状态快照。
- 产品流程上，风险事项应经过指派复核后再进入报告版本。
- Ontology 动作、风险事项、证据、复核和报告版本共同写入决策审计链。

## 4. 业务人员与技术人员协作流程

目标配置顺序是“先沉淀公司业务资产，再按需用内置验证 Agent 或外部 Agent 验证能力”。内置 Agent 不是建模、数据接入、权限配置、版本发布或孪生运行的前置条件；没有内置 Agent 也可以完成前六步并通过外部能力接口验收：

1. **选择或创建业务领域**
   - 公司内部共用一套模型库；业务人员或技术人员在企业模型公共顶部创建、选择和管理。
   - 先明确目标流程、非目标流程、负责人和验收人。
2. **连接并治理数据源**
   - 添加业务数据库连接并测试。
   - 读取远端表清单，只采集需要参与业务的表。
3. **在企业模型中心梳理业务**
   - 定义对象、属性、关系、事件、状态和动作。
   - 围绕业务对象配置查询词汇、指标口径和业务规则，不再创建第二套语义对象。
   - 技术人员按对象数据源、指标计算、关系连接和字段映射完成物理绑定；表和字段优先从已采集 Schema 中选择，原始 SQL 与 LogicForm 收入高级配置。
   - 通过稳定 `object_key` 串联业务对象、查询口径和数据映射。
4. **校验并发布企业模型**
   - 在“校验发布”集中执行草稿校验、查询运行时检查、语义快照和统一版本管理。
   - 校验主键、字段映射、关系、指标和动作引用；将语义资产快照与 Ontology release 绑定，校验后激活并按需更新验证检索索引。
5. **运行数据孪生**
   - 业务人员可预览并核对结果；技术人员执行受控写入同步，并检查对象/关系实例、动作记录、数量、状态和来源。
   - 生产级定时增量同步、身份冲突和坏数据报告后续补齐。
6. **检查并发布业务能力**
   - 在能力发布中心核对对外 Query Capability，以及仅供内部验证的对象查询和 Action 工具。
   - 当前已有独立调用凭据、Query 授权和调用审计，但不是完整生产网关。
7. **配置内置验证 Agent（可选）**
   - 绑定大语言模型、向量模型和用于调试的领域/数据源；首个真实试点建议只绑定一个默认领域和一个业务数据源。
   - 配置推荐问题，用于验证能力是否符合业务预期；第三方 Agent 可直接调用能力合同，不必创建这里的 Agent。
8. **配置用户与数据权限**
   - 创建或启用用户。
   - 旧验证账号按需分配可访问智能体；业务人员和技术人员直接按业务领域工作。
   - 以业务领域为正式权限主体维护数据源、表白名单、列权限和脱敏；只在迁移旧配置时维护 Agent 兼容权限。
9. **按需调整运行配置**
   - 修改 Schema 召回阈值、候选表数量或节点 Prompt。
10. **进入垂直场景验证**
    - 组织问数、风险事项、复核、报告版本、受控动作和审计回放。

兼容说明：`enterprise_workspace`、`semantic_domain.workspace_id` 以及 `semantic_domain.agent_id` 等字段仅用于单公司部署的历史兼容；新建和导入领域统一写入默认内部容器，业务模型的实际管理边界是 `domain_id`。`agent_semantic_domain`、`agent.semantic_domain_id` 和 `agent_datasource` 主要服务于本项目内置验证 Agent；`agent_table_permission/agent_column_permission` 只用于旧领域迁移。删除验证 Agent 不删除业务领域和企业模型；若仍承担旧权限适配，则必须先迁移或撤销相关授权。数据源页已提供领域级表白名单、列权限和脱敏的第一版维护入口。

## 5. 当前验证账号流程（兼容链路，不是目标产品角色模型）

本节只记录现有 `admin/user` 兼容账号和内置验证 Agent 如何完成演示与回归。平台角色仍只有业务人员和技术人员；`user` 仅保留历史验证客户端只读链路，不再扩建独立的兼容账号领域授权体系。

### 5.1 登录与验证客户端兼容流程

- 新注册账号默认映射为业务人员；技术人员账号当前由 `admin` 兼容账号创建或调整。
- 业务人员和技术人员直接按业务领域访问企业模型；旧 `user` 账号才需要验证客户端兼容授权。
- 验证客户端只用于调试和回归，不拥有企业模型资产。

### 5.2 日常问数

1. 在需要调试时选择验证智能体或使用默认验证客户端。
2. 用自然语言提出业务问题。
3. 查看系统的语义增强、语义资产、Ontology 命中、候选表字段和查询过程。
4. 查看最终答案、SQL、结果表；明确要求分析、趋势、报告或图表时进入深度分析。
5. 在同一会话中继续追问、修改时间/维度、重新执行或分析上一轮结果。

### 5.3 从问数进入风险交付

1. 在已完成的查询结果上点击“创建风险事项”。
2. 确认风险标题、分类、严重度、指派复核人和可选 Ontology 对象。
3. 系统自动固化查询证据和分析证据，不需要手工复制 SQL 与结果。
4. 进入风险交付工作台补充证据或查看完整证据链。
5. 被指派的业务人员或技术人员执行复核；创建人不能复核自己创建的事项。
6. 创建草稿报告及 V1，后续修订必须创建新版本。
7. 技术人员完成最终定稿。

### 5.4 Ontology 业务操作

- 业务人员可以查看和核对所属领域的对象、关系、动作和发布版本；技术人员负责运行配置。
- 业务人员可以预览同步结果并查看对象、关系实例；只有技术人员可以执行写入型同步。
- 只有满足动作 `allowed_roles`、状态、发布版本、参数、前置条件、审批单号和对象版本校验时才能执行动作。
- 业务人员查看自身相关动作记录，技术人员可查看全部运行记录。

## 6. 智能问数运行流程

当前问数不是简单的“问题直接交给模型生成 SQL”，而是受控的持久任务循环：

```text
加载 checkpoint
-> 判断本轮是新问题、追问、重试还是继续分析
-> 每次只选择一个白名单动作执行
-> 保存 observation 和 checkpoint
-> 完成、等待补充或进入下一动作
```

一次新的数据问题通常按以下链路推进：

1. **意图识别**：区分数据查询、闲聊和元数据问题。
2. **语义增强**：结合当前问题、历史问题和领域 rewrite 规则补全指标、维度、时间及 TopN。
3. **语义与 Ontology 召回**：优先按当前激活的统一企业模型版本加载固定的语义快照、对象、关系和按角色可见的动作定义，并校验两部分内容哈希；没有统一版本的历史兼容领域会显式记录实时定义回退警告。
4. **Schema 定位**：只在已绑定数据源、已采集 Schema 和智能体权限范围内，对表、字段和 JOIN 关系打分。
5. **LogicForm 生成**：把问题转换为指标、维度、过滤、时间、排序和限制等结构化意图。
6. **语义校验**：检查 LogicForm 是否引用了合法资产及可用维度。
7. **确定性 SQL 编译**：命中语义层时由代码编译 SQL；语义层不足或编译失败时才进入受限 NL2SQL 兜底。
8. **SQL 安全与权限校验**：限制为单条只读 SELECT，检查表权限，强制结果上限。
9. **业务库执行与脱敏**：执行查询，并按列级策略对结果做隐藏或脱敏。
10. **回答或深度分析**：简单问题直接整理答案；分析类问题继续进入 Python 安全执行、图表和 Markdown 报告。
11. **持久化**：查询过程、LogicForm、SQL、结果、报告写入 `chat_history`；可续跑状态写入 `agent_task_checkpoint`。

### 6.1 系统如何识别相关表和字段

表和字段不是只靠大模型猜测，而是多种信号共同打分：

- 用户原问题和语义增强后的关键词。
- 语义指标、概念、规则和映射中的名称、描述与同义词。
- Ontology 对象、属性、关系和动作命中结果。
- 已采集表名、表注释、字段名、字段注释和外键。
- 领域配置的 recall profile、schema hint 和业务分组。
- 系统参数中的相对分数阈值和最大候选表数。

最终只有通过用户、智能体、数据源、表和列权限筛选后的 Schema 才会进入 LogicForm、SQL 兜底上下文和查询执行。

## 7. 数据如何串联

### 7.1 三类存储

| 存储 | 保存内容 | 写入边界 |
|---|---|---|
| 业务数据库 | 客户、申请、账户、财税凭证等真实业务数据 | 问数和 Ontology 同步只读；当前 Ontology 动作不直接更新业务库 |
| 管理数据库 | 用户、智能体、模型、数据源、Schema、语义资产、Ontology、会话、风险、报告和审计 | 平台配置和业务工作流的主要落库位置 |
| 向量存储 | 语义资产 embedding | 用于语义召回；失败时可降级为关键词召回 |

### 7.2 关键关联标识

| 标识 | 串联范围 |
|---|---|
| `user_id` | 用户身份、会话归属、任务、动作、复核和审计 |
| `workspace_id` | 单公司部署的内部兼容字段，不是产品租户边界 |
| `agent_id` | 内置验证 Agent 的配置、用户授权和 Chat 兼容运行边界；不表示领域资产所有者 |
| `datasource_id` | 物理数据库、已采集 Schema、表列权限和 SQL 执行 |
| `domain_id` | 企业模型、数据映射、Ontology、能力、风险事项、报告和审计的业务领域 |
| `session_id` | 一段多轮对话 |
| `trace_id` | 一次问数结果与风险证据的精确血缘 |
| `task_id / turn_id` | 持久任务与某次用户轮次 |
| `ontology_release_id` | 风险、证据、报告版本和动作所依据的业务模型版本 |
| `subject_object_id` | 风险事项关联的 Ontology 对象 |

### 7.3 核心数据链路

```text
datasource
-> meta_table / meta_column
-> semantic_mapping / semantic_metric / semantic_relation
-> LogicForm
-> compiled_sql
-> business database result
-> chat_history + trace_id
-> risk_issue
-> risk_evidence + risk_issue_review
-> risk_report + risk_report_version
-> decision_audit_event / decision_audit_head
```

Ontology 对象同步采用两层属性：

```text
展示和动作校验属性 = source_properties + overlay_properties
```

- `source_properties` 来自业务库只读同步。
- `overlay_properties` 来自 Ontology 动作或技术人员对非身份字段的本地状态变更。
- 同名字段以 overlay 为准，因此刷新业务库不会覆盖已执行动作的本地结果。
- 对象主属性属于稳定身份，创建或同步后不可通过实例编辑修改；前端锁定主属性，后端同时拒绝绕过页面的主标识变更。

对象实例按数据来源继承不同权限，不按页面一刀切：

- `source_kind=manual/bundle`：属于平台内创建或导入的对象，不依赖业务数据源白名单；可在孪生运行中正常查看和维护。
- `source_kind=database`：虽然对象副本存入管理库，业务数据属性仍继承来源数据源的领域表/字段权限和脱敏规则；未配置领域权限时不返回这些对象。
- 关系实例任一端为不可见的数据库对象时，整条关系隐藏；手工对象之间的关系不依赖业务库权限。
- 同步预览/执行、Query Capability 和任何真实业务 SQL 始终要求领域数据权限，不能因为允许查看手工对象而绕过白名单。

因此，领域尚未配置数据权限时，孪生页面仍可打开并展示手工对象或空状态；需要读取或同步业务库数据时，再明确提示配置领域表/字段白名单，不要求创建 Agent。

## 8. 权限边界

### 8.1 页面与配置权限

| 能力 | 业务人员 | 技术人员 |
|---|---:|---:|
| 对话 | 使用验证客户端进行调试 | 配置并使用验证客户端 |
| 风险交付 | 参与业务复核和结果确认 | 组织技术验收并定稿报告 |
| 企业模型 | 维护业务定义和模型草稿 | 维护数据映射、校验、发布和回滚 |
| 孪生运行 | 查看实例、动作记录和预览结果 | 查看并执行写入型同步 |
| 能力发布中心 | 查看和验证能力 | 管理调用方、授权和审计 |
| Ontology 动作执行 | 按 `allowed_roles` | 按 `allowed_roles` |
| 智能体、模型、数据源 | 不可以 | 可以 |
| Prompt、系统参数、用户管理 | 不可以 | 可以 |

### 8.2 数据访问边界

当前兼容链路的数据访问依次经过：

```text
用户/调用方是否可访问业务领域与能力
-> 业务领域是否绑定数据源
-> 表是否在允许范围
-> 列是否允许或需要脱敏
-> SQL 是否为安全只读查询
```

当前精确规则：

- 表权限采用默认拒绝：只有明确允许的表可以进入 Schema、SQL、对象和同步链路。
- 未配置表白名单时，不允许访问该数据源中的业务表。
- 未配置列权限时默认允许且不脱敏。
- 列脱敏支持 `redact`、`partial` 和 `hash`。
- SQL 过滤值使用命名参数绑定；执行前检查表和禁止字段，字段别名/表达式继承物理列脱敏策略。
- 对象、关系、Action 和同步返回共用同一权限主体与脱敏规则；同步落库保存真实值，响应再脱敏。
- 从对话固化 Ontology 对象证据时，使用该次查询所用的权限主体再次过滤字段并执行脱敏。

权限链路已同时覆盖“用户 -> 业务领域 -> 内置验证 Agent”和“第三方调用方 -> 业务领域 -> Query Capability -> 数据边界”。正式数据边界由领域级表列权限承载；第三方调用不需要创建内部 Agent，`execution_agent_id` 仅保留为旧领域权限迁移兼容字段。

### 8.3 风险与报告权限

- 业务人员只能把自己的对话结果转换为风险事项；技术人员可跨验证会话做技术验收。
- 创建人不能复核自己创建的风险事项，并且复核人必须是指派人员。
- 业务人员可以创建风险事项、补充证据、创建草稿报告和新版本。
- 报告定稿由技术人员执行；定稿后不能继续创建新版本。

## 9. 当前实现边界（阶段进度唯一见路线图）

企业模型入口、孪生运行和能力发布入口已形成第一版代码切片；企业模型已按对象中心的业务模型、集中数据绑定和校验发布流程组织，并补充对象映射向导与安全编辑。P1/P2/P3 仍分别有真实领域、增量运行时和完整能力治理等未完成项，当前仍处于真实业务接入前的工程验收阶段。具体阶段、优先级、状态和验收进度唯一以 [Ontology 产品路线图](./ontology-product-roadmap.md) 为准，本文不另维护日期化进度结论。

以下能力当前没有实现，文档和演示中不能当作已有能力：

- 对话 ReAct 尚未自动调用 Ontology 动作；动作主要从孪生运行页或受控内部工具执行。
- Ontology 同步由孪生运行页/API 手动触发，不是 CDC 或后台定时任务；写入型同步仅技术人员可执行。
- Ontology 动作当前只更新管理库对象和 overlay，不直接写回 ERP、催收、短信或业务数据库。
- `requires_approval` 当前表示执行时必须提供审批单号，不是完整审批流。
- 尚未实现动态 ABAC、生产级动作幂等与失败补偿、分布式图事务。
- 对话已支持显式选择业务领域并在 checkpoint 中保存领域和模型版本；未选择时仍会回退 Agent 默认领域。语义向量索引已按领域、企业模型/语义快照版本和 Embedding 配置版本共享，Agent 只用于选择验证时采用的模型配置。
- `enterprise_model_release` 已把语义快照和 Ontology 发布绑定为统一激活版本；版本 diff 和依赖影响分析仍未完成。
- 孪生运行遵循“规则 B”：读取并校验 active release 的冻结 Ontology 定义；草稿可继续编辑，不影响当前同步。若草稿删除或重命名 active release 依赖的稳定 key，因无法解析原有存储身份仍会阻断运行。当前仍缺少增量调度、删除检测、身份合并和完整状态历史。
- 当前报告创建接口尚未强制要求所绑定风险事项已经复核或确认，复核后出报告目前属于产品流程约束。
- 贷款数据和规则只用于技术演示，不能作为真实业务判断依据。
- 当前没有多租户或多企业空间产品能力；`enterprise_workspace` 只作为单公司部署的内部兼容容器保留。
- 数据源仍被业务领域引用时禁止删除；业务领域一旦产生版本、对象、运行或审计记录，禁止硬删除，应改为停用，以保留企业资产和追溯链。
- 业务领域或数据源被停用后，管理页面仍可查看和调整配置，但查询、动作和孪生运行会被阻断。
- 外部能力当前只发布 Query Capability；能力中心尚未包含 SDK、Decision/Action 外部调用、灰度、限流、配额、SLA 和依赖影响分析。
- 通用 Decision Capability、预测模型治理和预测结果反馈闭环尚未形成。
