## 1. 项目目标

问渠 WenQu 的目标是建设 **公司内部使用的 Ontology 驱动企业运营数字孪生与智能决策平台**。平台先把公司的业务理解和数据沉淀为可复用能力，再提供给不同的第三方 Agent 和业务应用。近期优先把企业模型、数据运行时和能力发布中心做扎实，使业务和技术团队可以共同完成：

### 第一性目标

> **让业务语义成为企业资产，让数据库成为数据来源，让 Agent 成为能力消费者。**

这句话是后续产品设计、技术实现和验收的最高判断准绳：

- **业务语义是企业资产**：对象、关系、属性、状态、规则、动作、指标和版本属于业务领域/企业模型，不属于某一个 Agent。
- **数据库是数据来源**：表、字段、SQL、API 和文件是实现映射与运行时的来源，不直接替代业务模型。
- **Agent 是能力消费者**：内置 Agent 只用于调试、回归和验收；外部 Agent 通过已发布的能力合同消费同一套模型、权限、版本和审计。

平台不是在数据库前面增加一层字段翻译，也不是把 Agent 做成企业模型的拥有者。Ontology 的价值必须体现在：同一业务语义可以被多个 Agent 和业务应用复用；物理表结构变化时主要调整映射而不是重写业务口径；查询和动作可以追溯到对象、关系、数据来源、发布版本和调用权限。

1. 用对象、属性和关系表达公司的统一业务语义，并使其独立于具体 Agent 和物理表名。
2. 用动作定义可执行的业务操作及其权限、参数、前置条件和状态变更。
3. 对本体进行校验、发布和版本留痕。
4. 录入或接入业务对象实例，并通过动作形成可审计的决策闭环。
5. 将已发布企业模型转化为 Query / Decision / Action Capability，供本项目验证 Agent 和外部第三方 Agent 复用；调用方不拥有、不复制企业模型。

财税报告交付、贷款风控和智能问数是平台上的垂直应用与验证场景。本项目内置 Agent 只是调试、回归和验收客户端；Agent 不拥有本体资产，第三方 Agent 不需要先在本项目创建 Agent。

当前的事件和状态主要通过语义概念、对象属性、动作效果与审计记录表达；独立事件流、历史状态时间线和持续订阅不属于已完成能力，随孪生运行时逐步建设。

本期不建设通用 RDF/OWL 推理引擎，也不建设复杂多 Agent 编排。产品定位是 Palantir 风格的运营本体：业务语义、数据状态、决策逻辑、动作和治理共同组成可运行的企业数字孪生。多企业、租户和企业空间不是当前产品目标。

## 2. 用户与核心流程

| 角色 | 核心任务 |
|---|---|
| 业务人员 | 定义对象、关系、指标、业务动作并确认业务口径，提交模型草稿 |
| 技术人员（包含数据库工程师） | 配置数据源、Schema、物理映射、权限、同步、模型发布和运行维护 |

平台产品角色只有业务人员和技术人员（包含数据库工程师）。现有 `admin` 映射为技术人员兼容权限，`user` 仅保留历史验证客户端只读兼容，不作为新的产品角色；不建设独立普通用户体系。第三方 Agent、业务应用及其开发者属于外部调用方，不计入平台角色。

当前开发与讲解阶段暂由项目开发者使用 `admin` 账号同时完成业务和技术操作，本轮不增加工作模式或新的权限控制；待真实业务人员和技术人员参与后，再按已确定的产品角色落实编辑边界。

主流程：选择业务领域 -> 建企业模型与数据映射 -> 校验发布 -> 同步对象状态 -> 发布业务能力 -> 内置验证 Agent/第三方 Agent 按授权调用 -> 审计与反馈。

### 2.1 业务领域为什么必要

本项目只有一个公司内部环境，不建设多企业空间或租户层级。**业务领域**用于把公司的复杂业务拆成可独立梳理、发布、验收和复用的范围。

- **业务领域**回答：这是客户、财税、授信还是风险管理模型，由谁负责，使用哪些数据和规则。
- **企业模型**回答：业务对象、指标、关系、状态、规则和动作是什么。
- **能力发布中心**回答：这些定义如何以稳定的 API/SDK 合同被不同 Agent 调用。

目标关系是“一份公司企业模型被多个 Agent 复用”，而不是“每个 Agent 私有一份本体”。

实现边界：当前 Chat 已支持显式选择 `domain_id`，未选择时才回退内部验证 Agent 的默认领域；模型配置和会话归属仍保留 Agent 兼容层。外部 Agent 的正式调用直接面向 `domain_id + release_id + caller context`，不依赖内部 Agent 配置。

### 3.1 P0 平台兼容骨架

P0 不重写现有 Ontology、查询语义和问数链路，只调整产品主从关系并提供统一入口：

| 能力 | P0 第一版 | 明确不包含 |
|---|---|---|
| 业务领域归属 | 复用现有领域，保留单公司内部兼容容器和 Agent 消费绑定 | 多企业空间、租户隔离、组织树和跨企业治理 |
| 企业模型中心 | 在同一入口管理原查询语义和本体建模资产 | 一次性合并所有底层表和服务 |
| 孪生运行 | 集中展示同步任务、对象实例、关系实例和动作执行记录 | 后台定时任务、CDC、身份解析、完整状态历史 |
| 能力发布中心 | 集中展示和调用现有对象查询、Query Capability、Action 工具 | 生产级网关、订阅、灰度、配额、SLA 和完整发布审批 |
| 能力验证客户端 | 保留内部 Agent/对话配置，用于调试、回归和验收 | 把内部 Agent 当作第三方接入网关，或建设复杂多 Agent 编排 |

P0 的 Agent 绑定只是内部验证客户端的兼容机制，不是企业模型的所有权，也不要求外部 Agent 先创建内部 Agent。

## 4. V1 技术架构

| 层次 | 现有复用 | 本期新增 |
|---|---|---|
| 接入与数据 | 数据源、Schema 采集、MySQL 客户端 | 对象实例和关系实例运行时 |
| 业务领域 | 现有语义领域与 Agent 配置 | 单公司领域归属和验证客户端消费绑定 |
| 企业模型 | 语义领域、概念、指标、映射、Ontology 对象和动作 | 统一产品入口和稳定关联边界 |
| 逻辑与动作 | 语义规则、LangGraph、权限角色 | 动作参数、前置条件、效果和执行器 |
| 治理 | JWT、管理员权限、语义快照 | 本体校验、发布快照、动作审计 |
| 体验 | Vue、Element Plus、ECharts | 企业模型、孪生运行和能力发布中心统一入口 |

### OSDK 术语边界

本项目借鉴 Palantir OSDK 的类型化能力访问思想，但不把 OSDK 当作本体建模层。当前开发统一采用以下边界：

- `Query Capability`：只读对象查询、过滤、关联、聚合、排名、趋势和指标计算；可由 `LogicForm` 与确定性 SQL 编译链路承载。
- `Action Capability`：创建、修改、审批、状态变更或其他有业务副作用的操作；由 `OntologyActionType` 和受控动作执行器承载。
- `Typed Capability Facade`：为 Chat、Agent、报告和风险流程提供统一的类型化访问契约，底层可以继续复用现有 SQL/API 和 Ontology 服务。

第一阶段优先建设 `Query Capability`，已有动作模型继续保留并作为后续写入能力；只读查询不得命名或实现为写入 Action。详细的对齐和增量开发计划见 [Ontology / OSDK 对齐与 DataQueryAgent 增量改造计划](./ontology-osdk-alignment-plan.md)。

## 5. 数据与动作契约

### 对象类型

- `object_key`：领域内稳定且唯一的英文标识。
- `primary_property`：实例业务主键，发布前必须存在。
- `display_property`：实例的人类可读展示字段。
- `properties`：支持 string、text、integer、number、boolean、date、datetime、json。

### 动作类型

- `parameters`：动作输入及 required/type/options 约束。
- `preconditions`：声明式条件，支持 eq/ne/in/not_in/gt/gte/lt/lte/exists。
- `effects`：把常量、动作参数、当前时间或当前用户写入目标对象属性。
- `allowed_roles`：存储层继续兼容 admin/user；产品角色由业务人员/技术工程师映射到该执行契约。
- `requires_approval`：V1 记录审批要求；自动审批流在后续版本接入。

### 决策血缘

每次动作执行记录 Ontology 领域、动作、目标对象、执行人、参数、决策上下文、执行前状态、执行后状态、结果和时间。

## 6. 非功能验收

| 类别 | V1 标准 |
|---|---|
| 安全 | 定义管理和发布仅管理员可操作；动作执行按 allowed_roles 校验 |
| 一致性 | 实例更新使用版本号递增；动作执行保留 before/after 快照 |
| 可维护性 | 企业模型独立于 Agent 生命周期；删除或更换 Agent 不应删除领域资产 |
| 可用性 | 所有核心操作可在工作台完成，不要求直接编辑 JSON |
| 可测试性 | 声明式校验和动作效果有单元测试；前端通过类型检查和生产构建 |

## 8. 开源复用策略

GitHub 调研结论是保留现有 FastAPI/MySQL 运营运行时，按边界引入成熟项目，而不是整体替换产品层。

| 项目 | 许可证 | 适用能力 | 决策 |
|---|---|---|---|
| LinkML | Apache-2.0 | YAML 模型、JSON Schema/Pydantic/SQL/SHACL/OWL 生成与 CI 校验 | P1 做 schema source-of-truth PoC，优先采用 |
| OpenMetadata / DataHub | Apache-2.0 | 技术元数据、Glossary、血缘、Ownership、连接器 | P2 二选一作为治理侧车，不嵌入核心运行时 |
| TypeDB | MPL-2.0 | 强类型实体/关系、TypeQL、多跳图事务 | 只有图查询规模被验证后才做 sidecar benchmark |
| TerminusDB | Apache-2.0 | JSON-LD、版本 diff、Git-for-data | 借鉴发布/分支设计；有强版本化需求时 PoC |
| Ontop / RMLMapper | Apache-2.0 / MIT | R2RML、SPARQL-to-SQL、RDF/JSON-LD 导出 | 作为标准交换和离线迁移工具 |
| OpenSPG | Apache-2.0 | 中文知识构建、实体对齐、规则推理 | 后续知识抽取/符号推理专项 PoC |
| NocoDB | Sustainable Use License | 表格化实例编辑 UX | 不复用代码，许可证不适合商业产品嵌入 |

任何依赖进入主干前必须完成许可证确认、SBOM、安全扫描和最小 benchmark。历史调研依据见 [2026-08 开源项目调研快照](./archive/ontology-open-source-evaluation-2026-08.md)。

## 9. 上线指标

- 首个业务域从建模到发布不超过 5 个工作日。
- 一个已发布领域至少包含 3 个对象、2 个关系和 1 个可执行动作。
- 关键动作执行记录完整率 100%。
- 本体校验未通过时发布阻断率 100%。
- 试点流程人工切换系统次数和平均决策时长可被持续度量。

核心验收不是“本项目 Agent 能回答”，而是：给定同一 `domain_id + release_id + capability + 参数`，内置验证 Agent 和外部 Agent 应命中同一业务口径、得到可比结果，并保留可关联的 trace/审计信息；修改验证 Agent 的 Prompt 或模型，不应改变企业模型定义。

在真实测试库完成“允许/拒绝/脱敏、同步样例核对、激活版本固定、内外部调用一致性”验收前，只接入脱敏测试库或合成数据，不接生产敏感表。具体操作按 [业务领域与数据接入手册](./business-data-onboarding.md) 执行。
