企业模型与孪生运行使用说明

先把业务讲清楚，再让数据运行起来

企业模型负责定义业务，孪生运行负责把数据库记录变成可识别、可关联、可追踪的业务对象。

一句话理解

业务人员说明数据代表什么，数据库人员说明数据在哪里，平台把两者组成可供 Agent 使用的企业数字孪生。

更新日期：2026年9月8日

两个模块分别回答什么问题

它们不是两个互相独立的功能。企业模型是定义，孪生运行是定义落到真实数据后的运行结果。

定义

企业模型

回答：企业业务应该怎样理解？

定义
客户、贷款申请、账户、关系、状态、动作、指标和规则。
连接
把业务术语映射到数据库表、字段、关联路径和只读查询。
产出
经过校验并可激活的统一企业模型版本。
运行

孪生运行

回答：企业当前实际发生了什么？

读取
按照已激活模型和领域权限，读取业务数据库中的真实记录。
组织
形成对象实例、关系实例、当前状态、来源和动作记录。
产出
可查询、可追踪、可供 Agent 和业务应用消费的当前业务视图。

正确的业务顺序

不能先同步数据库，再回头猜数据代表什么。必须先形成业务定义和发布版本，运行时才知道如何读取、关联和保护数据。

企业模型：先完成业务和数据定义

1

确定业务领域

明确本次要梳理的是贷款、财税、供应链，还是其他业务范围。

2

定义业务本体

业务人员确认对象、关系、状态和动作，不从表名反推业务。

3

配置语义与数据

确认指标和规则，再由数据库人员绑定表、字段、关联条件和权限。

校验并发布

语义快照与 Ontology 发布绑定成统一版本。只有激活版本进入运行时。

→
运行门槛

草稿修改不会直接改变正在使用的模型。

孪生运行：再把真实数据变成业务对象

4

预览映射结果

先抽取少量数据核对主键、字段含义、类型和权限，不写入对象实例。

5

同步业务对象

将数据库记录按模型转换为对象实例，并建立可确认的业务关系。

6

查看当前孪生

查看对象状态、数据来源、版本、关系和动作记录，供后续能力调用。

关键交接物：两个模块之间传递的不是一段 SQL，而是一个已校验、已激活、可追踪的统一企业模型版本。

业务人员和数据库人员怎么配合

业务人员负责判断业务含义是否正确，数据库人员负责证明数据确实能支撑这些定义。

先确认业务，再确认数据，最后由平台发布运行。

任何一方都不需要独自完成全部配置。业务口径和物理数据绑定必须共同确认。

业务人员

说明“客户、申请、审批状态、申请数量”分别是什么，确认对象、关系、指标和规则是否符合实际业务。

数据库人员

确认数据在哪张表、使用哪个主键、字段如何关联、枚举值代表什么，并配置只读映射和数据权限。

平台管理员

组织校验、创建统一版本、激活模型、执行预览和同步，并检查错误、版本和运行记录。

为什么不直接让 Agent 查数据库

数据库只说明数据怎么存，不完整说明业务怎么理解、怎么算、谁能用，以及结果依据哪个版本。

核心价值是把业务理解从个人经验和临时 SQL，变成可以持续复用的企业资产。

数据库结构变化时，主要调整数据映射。Agent 或业务应用变化时，企业模型仍然保留并可继续复用。

统一口径同一个指标和对象由企业模型统一定义。
减少重复不同 Agent 不需要各自重新理解数据库。
安全可控数据访问受领域表和字段权限约束。
全程可追踪结果可关联模型版本、数据来源和运行记录。

当前阶段需要知道的边界

下面这些限制必须讲清楚，避免把当前原型理解成已经完成的生产级自动运行平台。

现在已经能做什么，暂时还不能做什么

已支持企业模型草稿、校验、统一版本激活和回滚。
已支持按领域权限预览和手动分页同步业务对象。
手工创建的对象可直接查看，业务库同步对象继续继承来源权限。
尚未实现 CDC、后台定时增量同步和跨系统自动身份合并。
Ontology 动作目前更新平台对象或叠加状态，不代表已写回业务数据库。
内置 Agent 只用于调试和验收，企业模型不属于某个 Agent。

业务语义成为企业资产，数据库成为数据来源，Agent 成为能力消费者。

企业模型负责把业务讲清楚，孪生运行负责让真实数据按照这套业务定义持续形成当前企业状态。
