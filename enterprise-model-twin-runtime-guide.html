内部 1.0 试点版说明

让企业业务成为 AI 能用的共同语言

问渠把业务定义、真实数据和可调用能力串成一条链，供不同 Agent 和业务应用使用同一套企业模型。

平台服务公司内部的业务和技术协作。业务语义是企业资产，数据库是数据来源，Agent 是能力消费者。

平台只有两个使用角色

数据库工程师属于技术人员的专业分工。外部 Agent 和业务应用是调用方，不是本平台的第三类角色。

业务人员

负责确认业务到底是什么意思，以及结果是否符合实际工作。

  • 明确业务范围、核心问题和验收口径。
  • 定义并确认对象、关系、状态、指标、规则和动作。
  • 核对映射预览、对象实例、查询结果和风险结论。
  • 参与风险事项复核，确认业务结果是否可以使用。

技术人员（包含数据库工程师）

负责把业务定义接到真实数据，并保证模型可以安全运行。

  • 配置数据源、Schema、表列权限和脱敏规则。
  • 完成字段映射、模型校验、版本发布和受控回滚。
  • 执行孪生预览与同步，维护能力授权和调用审计。
  • 维护模型、Prompt、系统参数、用户配置和运行环境。

当前开发验证阶段由项目开发者使用 admin 账号同时完成业务和技术操作；业务人员与技术人员的联合验收安排在开发封板后。admin/user 和内部验证 Agent 绑定只是兼容实现，不是额外产品角色。

全部功能模块，分成三组

主链负责沉淀和运行企业能力，验证与应用负责使用能力，横向支撑负责配置、权限和追踪。

底座主链

这是平台长期建设的核心部分

/enterprise-model

治理与业务领域

确定业务范围、负责人和数据访问边界。业务领域是公司内部的模型管理范围，不是多租户空间。

输出：可管理、可验收的业务范围
/datasource

数据源与元数据

测试只读连接，选择需要的表，采集字段结构，并配置领域表白名单、列权限和脱敏。

输出：可安全使用的数据来源
/enterprise-model

企业模型中心

把业务本体和查询语义放在同一入口。对象、关系、状态、动作、指标、规则和映射共同组成企业模型。

输出：模型草稿、映射和校验结果
企业模型子区

版本发布

将语义快照与 Ontology 发布绑定，联合校验后激活。运行、查询和审计都记录实际使用的版本。

输出：统一企业模型版本
/twin-runtime

数据处理与孪生运行时

先预览，后同步，把数据库记录转换为有身份、有状态、有来源的对象和关系实例。

输出：对象、关系、状态和运行记录
/capability-center

能力发布中心

将模型和运行结果整理为稳定能力合同。当前已支持外部只读 Query、独立调用凭据、授权和审计。

输出：外部 Query 入口；Decision / Action 外部出口后续建设

验证与应用

用于证明底座能力在真实场景中有用

Agent / 对话页

内置 Agent 与对话验证

用自然语言验证模型、查询和结果。它是调试、回归和验收客户端，不拥有企业模型。

定位：平台内置参考调用方
/risk-delivery

风险交付

将问题转成风险事项，固化证据，完成复核、报告和决策审计。贷款、财税只是垂直验证场景。

定位：底座之上的业务应用切片
外部调用方

第三方 Agent 与业务应用

不需要先创建本项目 Agent，直接按能力合同、业务领域、模型版本和调用权限使用平台能力。

定位：平台外部消费者，不计入平台角色

横向支撑

不改变业务口径，但保障整条链稳定运行

模型配置

配置大语言模型和向量模型，支撑理解、生成和语义召回。

Prompt

管理节点提示词。业务口径以企业模型为准，不由 Prompt 私自改写。

系统参数

调整召回阈值、候选表数量等运行参数，不定义业务指标。

用户、权限与审计

控制可见范围、可执行动作和调用追踪，贯穿所有模块。

一条业务从定义到使用

顺序不是先做 Agent，再反推数据库。正确顺序是先把业务和数据沉淀为资产，再开放给调用方。

1 治理与业务领域
确定范围

明确要解决的业务问题、对象范围、负责人和验收人。

产出：一个可管理的业务领域
2 数据源与权限
接入来源

连接只读业务库，采集需要的表和字段，配置允许范围及脱敏。

产出：受控 Schema 和数据边界
3 企业模型中心
讲清业务

业务人员确认对象、关系、状态、指标、规则和动作；技术人员完成物理映射。

产出：业务模型草稿和映射
4 版本发布
固定口径

创建语义快照和 Ontology 发布，联合校验后激活统一模型版本。

产出：运行时唯一依据
5 孪生运行时
组织状态

先预览，再同步对象和关系，检查实例数量、主属性、状态和来源。

产出：当前业务对象视图
6 能力发布中心
形成出口

先发布可复用的只读 Query；判断和有副作用的 Action 按后续能力治理逐步开放。

产出：当前可用的 Query 能力接口
7 Agent 与业务应用
消费能力

内置 Agent 用于验证，外部 Agent 和应用按授权调用同一能力。

产出：咨询、分析或受控处理结果
8 风险与审计
形成闭环

保留查询、对象、证据、复核、报告和动作记录，问题回到模型或映射修正。

产出：可解释、可复盘的业务结果

模块之间到底交接什么

模块不是简单跳转页面，每一步都向下一步交付一份明确的业务或技术产物。

业务领域 → 数据源治理

交接业务范围和数据使用边界，决定哪些表可以进入本次建模。

数据源治理 → 企业模型

交接可用的表、字段、类型、主键和权限，不替业务人员定义指标含义。

企业模型 → 版本发布

交接对象、关系、指标、规则、映射和动作的完整定义，校验失败不能激活。

版本发布 → 孪生运行

交接唯一运行版本，运行时发现定义或数据源漂移会阻断执行。

孪生运行 → 能力发布

交接对象状态、关系、来源和动作记录，形成可被调用的稳定能力契约。

能力发布 → Agent / 应用

交接能力名称、参数、权限、版本和追踪规则，调用方不复制企业模型。

应用结果 → 风险交付

将值得跟进的问题转成事项，自动固化查询和对象证据，进入复核与报告。

审计反馈 → 企业模型

定位是业务口径、字段映射、权限还是数据质量问题，再校验、发布和验证。

能力发布中心是平台的对外出口

发布企业模型解决“定义完成”，发布能力解决“别人可以稳定使用”。两者不是同一个动作。

Query

只读查询、过滤、关联、聚合、排名和指标计算。当前已有第一版外部调用能力。

当前：已实现第一版

Decision

基于规则或模型输出判断、原因和建议，后续形成通用决策能力。

状态：规划中

Action

创建、修改、审批和状态变化等受控操作。当前已有内部动作原型，正式外部出口后续建设。

状态：内部验证为主

调用关系：外部 Agent 提交能力名称和结构化参数，平台校验调用方、领域权限、模型版本和数据边界，再返回结果与追踪编号。调用方不需要先创建本项目 Agent。

数据库和平台数据如何串起来

业务库保存源系统事实，管理库保存模型和运行记录，向量存储帮助召回语义。三者分工不同。

业务数据库

保存客户、申请、账户、凭证等真实业务记录。平台以只读方式查询和同步。

平台管理数据库

保存用户、领域、数据源、模型、对象实例、会话、风险、报告和审计记录。

向量存储

保存业务语义的 embedding，用于检索相关概念、指标、规则和映射。

核心数据链路

datasource → meta_table / meta_column → 企业模型映射 → 统一模型版本 → 孪生对象与关系 → 能力合同 → Agent 或业务应用 → 结果、证据与审计

指标问数路径

已发布模型 → 编译只读 SQL → 读取业务库最新数据。结果重点是指标、维度和统计口径。

对象浏览路径

业务库 → 手动同步 → 读取孪生对象当前状态。结果重点是对象、关系、来源和状态。

三个数字不要混用：源表记录总量、已同步对象实例数、本次查询返回条数分别属于数据源、运行时和查询结果。

用贷款申请举例，完整走一遍

贷款只是技术验证场景，例子用来说明平台链路，不代表已经确认的授信或风险规则。

两类人员共同确认

业务人员说清楚

“贷款申请”是一笔有编号、状态和生命周期的业务对象；“按渠道统计”是申请数量按渠道分组。

技术人员接数据

loan_application_indicator 每行代表一笔申请，application_id 是主属性，channel 是申请渠道字段。

平台固定口径

企业模型同时保存申请对象、申请数量指标、渠道维度和字段映射，再通过版本发布固定这套定义。

应用消费结果

内置 Agent 或第三方 Agent 调用同一 Query 能力，得到可解释的分组结果；异常时进入风险交付。

从一行数据到一次调用

业务表字段业务库，只读来源
↓
申请对象与申请指标企业模型中的业务定义
↓
统一模型版本语义快照 + Ontology 发布
↓
Query 能力按申请渠道统计数量
↓
Agent / 业务应用结果结果、来源和 trace 可回查

第一次使用，按这个顺序

先用一个业务领域、一个只读数据源和 3-5 条真实问题做小闭环，再逐步扩大范围。

  1. 1
    业务人员提出问题列出要解决的业务问题，说明对象、指标和预期结果。
  2. 2
    技术人员建立来源连接数据库，采集相关表，设置表列权限和脱敏。
  3. 3
    共同完成企业模型确认对象、关系、状态、指标、规则和映射。
  4. 4
    校验并激活版本先校验语义和本体，再生成统一企业模型版本。
  5. 5
    预览并运行孪生核对主键、属性、关系、来源和实例数量，再执行同步。
  6. 6
    发布并验证能力授权 Query 能力，用内置验证客户端和外部调用方做同题验收。
  7. 7
    处理异常并留痕进入风险交付或审计记录，定位问题后回到模型、映射或权限修正。
  8. 8
    形成可复用资产保留版本、结果和追踪编号，让下一次调用不必重新解释数据库。

内部 1.0 怎么交付

当前版本先交付一个可用、可验证的公司内部试点，不把后续平台能力提前包装成已完成能力。

部署方式

使用 docker-compose.deploy.yml 启动 WenQu 后端和前端。部署包不会启动、初始化或覆盖公司已有业务 MySQL；平台管理库使用独立的 dataquery_agent 数据库。

管理员边界

当前由项目开发者负责管理员账号，并用兼容的 admin 账号完成业务和技术两类操作。业务人员和技术人员的真实账号验收放到开发封板后进行。

首个真实验收

封板后由业务人员和技术人员共同完成：范围确认、3–8 张核心表、表列权限、对象主键、关系键、指标口径、预览同步和 5–10 条标准问题。

当前开发测试领域

Build_test 是开发阶段留下的测试业务领域，不是正式业务领域。它目前没有 active release；切换到它时系统会提示先完成校验发布。本轮不删除、不擅自停用。

交付判断：现在可以准备内部试点部署；自动化验证为后端 615 passed，前端测试、Ruff 和生产构建均通过。正式引入业务人员和技术人员前，必须在目标服务器完成 Docker 首次构建，并在封板后完成真实角色和真实测试库联合验收。

当前边界必须讲清楚

当前版本定位为公司内部 1.0 试点。下面的边界帮助业务人员和技术人员准确理解可用范围，不把后续平台能力提前当成已完成能力。

现在可以做什么，暂时不做什么

可以在一个公司环境中按业务领域维护企业模型，不建设多租户和多企业空间。
可以把业务本体和查询语义统一维护，不把它们当成两套互相独立的产品。
可以预览和手动同步数据库对象，写入型同步由技术人员执行。
暂不提供后台 CDC、定时增量同步、跨系统身份合并和完整状态历史。
当前动作主要更新平台对象状态，不代表已经写回 ERP 或业务数据库。
内置 Agent 只做调试、回归和验收，企业模型不属于任何一个 Agent。
风险交付是贷款、财税等垂直验证场景，不是平台主线的唯一入口。
当前外部能力以 Query 为主，通用 Decision、外部 Action 和生产级治理仍在后续阶段。
严格运行页面没有 active release 时会返回明确的业务冲突提示，并引导先完成企业模型校验发布。
Docker 部署连接公司已有 MySQL；本项目部署 Compose 不会启动或覆盖业务数据库。

业务语义成为企业资产，数据库成为数据来源，Agent 成为能力消费者。

治理划定范围，数据源提供事实，企业模型负责理解，孪生运行组织状态，能力发布提供出口，应用和审计形成闭环。
